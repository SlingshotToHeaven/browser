## Signing and tracked-secret review

The release Gradle task is configured to produce an **unsigned**, minified, resource-shrunk APK. It does not read a home-directory keystore or any password. Use an owner-controlled signing station with a key kept outside the repository; don't store the key, passwords, or secret scan reports in CI, source, transcripts or logs. CI can assemble and check the unsigned APK without production signing material.

The local review used Detect Secrets 1.5.0 with verification disabled (27 plugins), signing assignment checks and a filename check for key material. It covered 442 files in the visible base `e83d2fa` and, separately, the candidate's tracked and non-ignored files, excluding the Git directory and ignored build/cache inputs. This checkout is shallow; the review is **not** a scan of full remote history, other branches, binary contents, local credential stores or service-side secrets.

## Non-Play distribution and size budget

This project will not be released on Google Play. Play approval, Play App Signing, AAB delivery and a Play-driven SDK retarget are out of scope. Android still requires a signed APK for direct installation. The candidate has a **new Android application ID, `com.browser`**. It installs alongside `com.privacy.browser.injection` or its prior `.debug` build, with independent app state; those packages cannot be upgraded in place to this one. Debug and release builds of `com.browser` use the same ID, so use isolated, authorized test installs when their signing identities differ.

- **Standalone APK:** the verification recipe below names `app-release-arm64-v8a.apk`, one signed APK containing code, resources and the ARM64 libraries, no splits. Do not call it a multi-ABI universal build. Evaluate the **20 MB** project goal as file length **≤20,000,000 bytes** (decimal MB; about 19.073 MiB). Record actual bytes, MB and MiB. The ZIP member categories and signature/padding overhead explain contributions; they are not installed disk use or a network-compressed estimate. Measure installed storage separately on a named Android device, with fresh install and seeded data/cache reported apart. Source file sizes don't count toward this measured gate.
- **Channel and platform checks:** Verify any requirements of the chosen non-Play distribution path. Check [Android developer verification](https://developer.android.com/developer-verification) where applicable to the target regions, stores and certified devices. Record the package ID, installed signing identity, minimum OS and ARM64 support. Require 16 KiB artifact and runtime checks for the supported devices, independent of store policy.

If the selected non-Play channel delivers splits instead, name the exact delivered set (e.g., base + `arm64-v8a` + density/language splits for a stored device spec), hash each APK and sum their file sizes against the byte budget. Also record store-reported download size or `bundletool get-size total` for a pinned device spec as a **different** measurement. Do not compare the AAB, `.apks` archive, or a locally generated universal APK to a device's delivered APK set. The measured unsigned size is not the signed delivery size; do not sacrifice protections or required native alignment to reach the budget.

## Build and verify the artifact (SDK-equipped release station)

1. Obtain an approved, clean source revision and resolve the [inventory gaps](release-inputs.md). Use a full JDK 17 and the pinned Gradle wrapper. For this checkout's target 34 SDK build, install `platforms;android-34`, `build-tools;34.0.0`, and `build-tools;35.0.0` for inspection. Install current Platform Tools (`adb`) for the device phase. If retargeting, pin and record the updated tools. Archive the [dependency resolution](release-inputs.md#build-inputs-and-declared-runtime-dependencies), merged manifest, Git revision, input hashes, R8 mapping and any usage report, away from the APK and public logs. Choose a versionCode higher than every baseline you will upgrade. Current versionCode `1` is not automatically an upgrade.
2. On Linux/macOS, run the [build/test/lint](../README.md#verify-without-a-device) checks and the following (commands illustrated with Build Tools 35.0.0). Stop on any failed check:

   ```sh
   sha256sum -c docs/native-arm64.sha256 docs/release-assets-build-inputs.sha256  # GNU coreutils; use shasum -a 256 -c on macOS
   ./gradlew --no-daemon :app:assembleRelease :app:lintRelease
   bt="$ANDROID_HOME/build-tools/35.0.0"
   unsigned=app/build/outputs/apk/release/app-release-unsigned.apk
   python3 -B tools/verify_release_apk.py apk "$unsigned" --build-tools "$bt" --inspect-only
   ```

   This last step checks non-debuggable release ID, ABI/inventory, uncompressed native ZIP entries, SDK `zipalign`, and packaged ELF headers. CI runs this **unsigned** path, not a signature or distribution test. Inspect the R8 mapping/DEX for `com.arthenica.ffmpegkit.FFmpegKitConfig` and the native method names plus `log`, `statistics`, `safOpen`, `safClose`. The narrow [consumer keep rules](../downloader/consumer-rules.pro) cover the native class lookup and private upcalls; only the release runtime test establishes that JNI works.
3. When authorized to sign, use a new restricted output directory and the correct existing channel key. Set `RELEASE_KEYSTORE` to a local keystore **path**, `RELEASE_KEY_ALIAS` to its alias and `RELEASE_CERT_SHA256` to the **public** expected signer fingerprint obtained independently of this new APK (e.g., the trusted prior release). Let `apksigner` prompt for passwords locally; don't put them on the command line, in env vars or in chat. For a lab upgrade use a dedicated test-only key and sign both builds with it; repeat with the **actual** distribution artifact and matching previous release identity before clearance.

   ```sh
   umask 077
   work=$(mktemp -d)
   aligned="$work/app-release-arm64-v8a-aligned-unsigned.apk"
   signed="$work/app-release-arm64-v8a.apk"
   "$bt/zipalign" -P 16 -v 4 "$unsigned" "$aligned"
   "$bt/apksigner" sign --ks "$RELEASE_KEYSTORE" --ks-key-alias "$RELEASE_KEY_ALIAS" \
     --v4-signing-enabled false --out "$signed" "$aligned"
   python3 -B tools/verify_release_apk.py apk "$signed" --build-tools "$bt" \
     --cert-sha256 "$RELEASE_CERT_SHA256" --max-bytes 20000000
   ```

   Align **before** signing. The verifier runs `aapt2 dump badging`, `zipalign -c -P 16 4`, parses the ELF `PT_LOAD` headers of *all* packaged `.so` files, and uses `apksigner verify --verbose --print-certs -Werr` with a required expected fingerprint and v2/v3 signature. Record the printed APK SHA-256, size/breakdown, versionCode and signer fingerprint. It does not modify or sign files. For a channel with a target SDK floor use `--min-target-sdk` with the required value. This standalone checker deliberately rejects split APKs and does not certify a multi-signer or key-rotation lineage. Validate any planned lineage on each supported OS through the channel's supported procedure.
4. **Split delivery, if selected:** build and validate the release bundle per channel; record `bundletool dump config --bundle=...` and expect `PAGE_ALIGNMENT_16K`. Check the actual delivered signed APK set for a pinned ARM64 device configuration. Verify every APK's signature against the trusted *app signing* certificate and that package/version match; check `zipalign -c -P 16 4` on each APK and confirm each delivered native entry is stored, not compressed (zipalign skips compressed entries). Extract the complete set's ARM64 `.so` files into a disposable folder, inventory every entry and run `readelf -W -l` on every library; require AArch64, congruent LOAD offsets/addresses and alignment of at least `0x4000`. Apply the same checks to each supported split set, including any ABI/config combinations that differ. `PAGE_ALIGNMENT_16K` in a bundle is a request, not evidence for the installed APKs. Use that exact set from the distribution channel or `adb install-multiple` when supported; don't rebuild or re-sign it after measurement.

### Playable mux fixture for the minified APK

On the **tester’s host**, use FFmpeg with `libx264` and AAC to generate known two-second video and tone. This is a separate fixture, not a public preview and not the FFmpeg used by the app:

```sh
python3 -B tests/fixtures/release_mux.py                   # binds 127.0.0.1:8018 only
# In another terminal:
adb reverse tcp:8018 tcp:8018
```

1. On a regular test tab with scripts allowed, visit `http://127.0.0.1:8018/`. Use **Grab Page Links** and select one `.m3u8` master at a time (not a child playlist). The masters require audio. Test `mux-ts.m3u8` (in-band AAC), `mux-fragments.m3u8` (ranged init/media parts, separate AAC rendition), and `mux-missing-audio.m3u8` (valid bytes but required audio missing). Wait for each job before trying the next. Expect 206s for each ranged init/media fetch and an actual mux attempt, not a saved playlist.
2. Open/share the two completed MP4s to a real video player, see moving frames and hear the tone. When collecting evidence on the host, use `ffprobe -v error -show_entries stream=codec_type,codec_name -of csv=p=0 <file.mp4>` and `ffmpeg -v error -xerror -i <file.mp4> -map 0:v:0 -map 0:a:0 -f null -`. Require both H.264 and AAC and a successful full decode. The missing-audio job must fail without a completed row/grant or published MP4. Reuse the controlled interruption/truncation cases in [DL-06](../DEVICE_TEST_CHECKLIST.md#downloads-storage-and-media-steps-0306) to confirm no raw/staged output is exposed.
3. Record the exact artifact hash, page size, successful local muxes and sanitized error category if something failed. Remove the reverse with `adb reverse --remove tcp:8018` and stop the host fixture. `--check` checks host generation/decode only. `StreamDownloadPlaybackTest` with `FFMPEG_TEST_BIN` similarly verifies the host mux path, not Android JNI.

## Stage only after all gates pass

1. Ensure the rights/notice and incident reviews, CI/lint, signed artifact, budget, upgrade matrix, lab/internal tests and physical device evidence are green. Agree on the release channel, version, monitoring window and stop criteria with the owner. Preserve the prior verified artifacts and evidence; use isolated staging or internal distribution first, then a small eligible cohort, then widen only after checking the gates again. No staging/deploy is authorized by this document.
2. Hold expansion on any startup, renderer, privacy, approval, file integrity, grant, migration or native/size regression. Review crashes/ANRs, success/failure category counts and paired traces using local or explicitly opt-in diagnostics. Do not collect URLs, signed queries, cookies, page content, transcripts, filenames or device IDs. Stop/withdraw the affected distribution; where a tested safe on-device switch exists, disable only the affected optional feature, otherwise use a higher-version compatible fix. Do not undo protections to make metrics pass.
3. **Downloads/bookmarks:** do not advise uninstalling, clearing all data, forcibly downgrading or copying raw SQL/WAL files from a live device. Preserve synthetic pre-upgrade snapshots for reproduction; the app disables OS app backup and has no general production restore promise. Keep checkpoints and completed files intact, don't assume a partial is complete, and try the documented Resume/Retry flow after fixing the underlying issue. If v8/v3 data is already written, ship a roll-forward build that reads those formats and tests migration idempotence. Never run a prior APK over newer state unless that exact downgrade is supported and tested.
4. **Sessions/rules:** keep a forward-compatible reader for Agent schema v2. Old provider replay data removed by the user is intentionally not restored; do not advise restoring a database that would reintroduce it. A missing/corrupt tab parcel is recoverable as a URL-only tab; an unreadable session index opens without restoring it rather than using stale legacy positions. Leave state for diagnosis instead of manually deleting user history. Keep custom rule copies in a user-controlled location where available; if a saved `FilterStore` snapshot is unreadable, the legacy rule fallback is read-only, not permission to overwrite it. Review a supported snapshot before committing replacement; don't force a legacy diff or bulk reset to fix one scriptlet. A roll-forward must read the saved tab generations and rule format that were already written.
5. **Worker:** follow the [separate v2 staging procedure](../cloudflare-worker/README.md#deploy-or-migrate-as-an-operator) with publishing off by default, a separate staging namespace, versioned schema check, and independent compatibility/health results in app and Worker. Keep old client configs/catalogs separate, preserve the v2 SQLite catalog and any legacy KV, and don't enable v1 diff import to recover service. On failure, turn off publishing, hold app rollout and roll forward with a reader/writer compatible revision; don't roll back storage migrations blindly. No live Worker was changed.

Use [the evidence table](../DEVICE_TEST_CHECKLIST.md#record-results-here). Record pass/fail/blocked for the exact build, device, ABI/page-size/provider, versionCode, signer fingerprint, APK bytes and hashes, and source/notice and dependency records. A host-only count, unsigned CI run, or successful test of a lab key cannot close `REL-01`.
