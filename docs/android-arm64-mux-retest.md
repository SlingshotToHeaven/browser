# Physical ARM64 mux retest: four positive cases

**Ready for a device runner; physical result pending.** This debug-only retest asks whether the same four downloads that stalled in `nativeFFmpegExecute` on the [ARM-translated API 34 emulator](android-emulator-download-batch.md#final-result) also stall on real ARM64. Use the original test methods and fixture generator. Do not rerun the download matrix, negative cases, emulator, or performance tests.

| Case | Synthetic input and expected HTTP evidence | File to play |
| --- | --- | --- |
| `stream-separate` | Direct `/video.mp4` and `/audio.mp4`, one full GET each | `separate.mp4` |
| `stream-ts` | `/mux-ts.m3u8` → `/ts-media.m3u8` → TS with in-band AAC at `/av.ts` | `transport.mp4` |
| `stream-fmp4` | `/mux-fragments.m3u8` and its two rendition playlists; exactly two HTTP 206 responses per track, for its init and media ranges | `fragments.mp4` |
| `stream-aes128` | `/encrypted.m3u8`, one synthetic key fetch and one encrypted TS fetch; the app decrypts before muxing | `encrypted.mp4` |

## 1. Build from the pinned source

On the **tester’s Linux or macOS host**, use JDK 17, Python 3.11+, Android Platform 34, Build Tools 34.0.0, current Platform Tools, OpenSSL, and an FFmpeg with `libx264` and AAC. Set `ANDROID_HOME` to that SDK. Use one authorized **spare ARM64 phone or tablet** running Android 14 or newer, USB-connected, unlocked, with **no `com.browser` or `com.browser.test` installation**. Select the owner profile, user 0. Do not uninstall or clear an existing profile to satisfy the preflight. This test does not use or change the old `com.privacy.browser.injection` package.

In Bash, from this repository checkout, use a fresh source archive so local edits can't enter the APKs. Stop if any line inside the build block fails.

```sh
git fetch --no-tags origin refs/heads/arena/bb0ffed3-browser
rev=0db99d319c91e9100f7b2c494201bc7449de614a
sdk=${ANDROID_HOME:?Set ANDROID_HOME to the Android SDK path}
work=$(mktemp -d "${TMPDIR:-/tmp}/browser-arm64-mux.XXXXXX")
(
  set -e -o pipefail
  mkdir "$work/source"
  git archive "$rev" | tar -xf - -C "$work/source"
  cd "$work/source"
  shasum -a 256 -c docs/native-arm64.sha256 docs/release-assets-build-inputs.sha256
  ./gradlew --no-daemon :app:assembleDebug :app:assembleDebugAndroidTest
)
cd "$work/source"
```

This builds the normal debug `com.browser` and its separate `com.browser.test` APK. The [SDK preflight](https://github.com/SlingshotToHeaven/browser/actions/runs/44731711247/job/136272863655) compiled both at this revision and checked their package IDs and the app ABI. It did not run Android or publish APKs. Compare the installed hashes to **your own** build, not to the CI build's debug-signed bytes. No production behavior, native library or signing configuration was changed for the retest.

## 2. Generate the fixtures and run the four tests

Use `ffmpeg=$(command -v ffmpeg)` for an installed generator. To match the original emulator encoder on a **Linux x86_64 host**, use its [exact pinned CLI](android-emulator-download-batch.md#earlier-runs-and-harness-fixes) instead:

```sh
asset=ffmpeg-n9.0.2-17-g2a571b6068-linux64-gpl-9.0
(
  set -e -o pipefail
  curl -fLsS "https://github.com/FFmpeg-Builds/FFmpeg-Builds/releases/download/autobuild-2026-09-30-13-08/$asset.tar.xz" \
    -o "$work/$asset.tar.xz"
  printf '%s  %s\n' '68ee646831adaae2495618346f3bba94ff207ff83bbd34d643e7004730d66269' "$work/$asset.tar.xz" \
    | shasum -a 256 -c
  tar -xJf "$work/$asset.tar.xz" -C "$work" "$asset/bin/ffmpeg"
)
ffmpeg="$work/$asset/bin/ffmpeg"
```

Another working CLI is fine for trying the same cases, but the generated bytes may differ. The report records the CLI version and the SHA-256 of each input. Host FFmpeg is **only** the generator and a fixture decode check; the device mux uses the APK’s bundled ARM64 JNI.

```sh
# Host-only preflight; stop if media generation or the host decode fails.
python3 -B tools/run_arm64_mux_retest.py --check-fixtures --ffmpeg "$ffmpeg"

adb="$sdk/platform-tools/adb"
"$adb" devices -l
# Read the spare device's serial from the list. Do not include it in the report.
printf 'Disposable USB device serial: '; IFS= read -r serial
python3 -B tools/run_arm64_mux_retest.py \
  --disposable --serial "$serial" --adb "$adb" \
  --aapt2 "$sdk/build-tools/34.0.0/aapt2" --ffmpeg "$ffmpeg" \
  --apk app/build/outputs/apk/debug/app-debug.apk \
  --test-apk app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk \
  --source "$rev" --report "$work/arm64-mux.json"
```

The [runner](../tools/run_arm64_mux_retest.py) checks the package IDs and target, installs with `--no-replace`, then verifies the installed APK hashes. It serves only the case fixtures on host loopback and uses a non-rebinding `adb reverse` for `tcp:8024`. Tests run one at a time using fresh app-private output folders. The runner removes its reverse when it exits; it does not reset, uninstall, root, or grant broad storage access on the phone. Do not bypass a preflight refusal or reuse a possibly unfinished attempt from a crashed test.

**Automated pass:** the real engine commits a `COMPLETED` row and the matching MP4, with no remaining file in the case folder except that MP4. Android finds H.264 and AAC, reads an AAC sample, decodes a 160×96 video frame, and runs `MediaPlayer` to completion. The runner also requires the matching HTTP observations and records MP4 size and SHA-256. A timeout, blocked prerequisite, or missing named instrumentation result is not a passing case. If a case stalls, keep the result and the recorded last row, mux-phase flag and `nativeFFmpegExecute` flag if present. Keep the original 25-second completion wait and 73-second runner limit; record any deliberate rerun separately. Remaining selectors stay `not-run` if the instrumentation runner dies or times out.
